# Архитектура «оркестратор ↔ субагенты»: проверенные факты и источники

Документ фиксирует архитектурные паттерны делегирования между ведущим агентом (orchestrator) и субагентами: какие приняты индустрией к 2026 году, какие отвергнуты, механизм каждого решения и первоисточник.

**Легенда статусов:**
- `доминирующий 2026` — паттерн, к которому сошлась индустрия.
- `отвергнут 2026` — паттерн, признанный консенсусом как источник сбоев.
- `ограниченная применимость` — работает только при выполнении явного условия.
- `[вывод]` — производное утверждение, выведенное из приведённых ниже фактов; отдельного источника именно на эту формулировку нет.

**Пометки источников:** `(primary)` — первоисточник (разработчик/авторы/препринт); `(secondary)` — вторичный обзор/синтез.

---

## 1. Базовые архитектурные паттерны

### 1.1. Orchestrator-worker (ведущий агент + параллельные субагенты)
**Определение.** Один ведущий агент планирует процесс, декомпозирует задачу и делегирует подзадачи изолированным субагентам, работающим параллельно, затем агрегирует их результаты.
**Статус.** `доминирующий 2026`.
**Механизм.** Суть поиска/исследования — компрессия: субагенты сжимают информацию, работая параллельно, каждый в собственном контекстном окне. Паттерн «координатор разбивает задачу — воркеры обрабатывают части в изоляции — координатор сшивает результат» известен в распределённых БД и планировщиках десятилетиями; новизна 2026 в том, что каждый узел — LLM, принимающий решения о маршрутизации на лету.
**Источник.** Anthropic, *How we built our multi-agent research system* (primary) — https://www.anthropic.com/engineering/multi-agent-research-system

### 1.2. Эфемерные изолированные субагенты с возвратом сжатого саммари
**Определение.** Субагент создаётся под конкретную задачу, имеет собственное контекстное окно, возвращает ведущему сжатый результат и завершается. Прямого peer-to-peer обмена между субагентами нет.
**Статус.** `доминирующий 2026`.
**Механизм.** Полным контекстом владеет только оркестратор; воркеры изолированы и возвращают компрессированное саммари. К этому паттерну сошлись несколько крупных вендоров, peer-каналы между воркерами убраны.
**Источник.** Anthropic (primary) — субагенты работают параллельно каждый в своём контекстном окне — https://www.anthropic.com/engineering/multi-agent-research-system ; синтез о конвергенции вендоров (secondary) — https://www.flowhunt.io/blog/multi-agent-ai-system/ , https://niteagent.com/blog/multi-agent-production-2026/

### 1.3. Peer-collaboration / общий «GroupChat» как транспорт координации
**Определение.** Несколько агентов делят общий канал/шину сообщений, задают вопросы друг другу и перечитывают весь транскрипт на каждом пробуждении.
**Статус.** `отвергнут 2026`.
**Механизм.** Перечитывание полного транскрипта раздувает контекст. Рассогласование между агентами образует отдельный класс сбоев, невозможный в одноагентной системе. Прямая формулировка механизма: действия несут неявные решения, а конфликтующие решения несут плохой результат.
**Источник.** Cognition, *Don't Build Multi-Agents* (primary) — https://cognition.ai/blog/dont-build-multi-agents ; синтез об утрате позиций peer-дизайнами (secondary) — https://www.flowhunt.io/blog/multi-agent-ai-system/

### 1.4. Single-writer / single-threaded
**Определение.** Состояние и решения накапливаются ровно в одном месте; параллельные писатели одного и того же состояния не допускаются.
**Статус.** `доминирующий 2026`.
**Механизм.** Два независимых накопителя состояния со временем расходятся; конфликтующие неявные решения дают деградацию результата. Практическая форма — map-reduce-and-manage: менеджер делит работу, дети исполняют, менеджер синтезирует и отчитывается.
**Источник.** Cognition, *Don't Build Multi-Agents* (primary) — https://cognition.ai/blog/dont-build-multi-agents ; Cognition, *Multi-Agents: What's Actually Working* (primary) — https://cognition.ai/blog/multi-agents-working

## 2. Состояние субагента между вызовами

### 2.1. Stateless-контекст на каждый вызов + внешнее состояние по ссылке
**Определение.** При многократных обращениях ведущего к субагенту в рамках одного ответа каждый вызов получает свежее контекстное окно. Тяжёлые рабочие артефакты (транскрипт, сырые результаты поиска) пишутся во внешнее хранилище и передаются ведущему ссылкой/хэндлом, а не телом.
**Статус.** `доминирующий 2026`.
**Механизм.** Ведущий держит в контексте только хэндл и краткое саммари — это сберегает его контекстное окно. Внешняя память переживает усечение контекста: ведущий сохраняет план в Memory именно потому, что при превышении ~200 000 токенов контекст обрезается, и план важно сохранить.
**Источник.** Anthropic (primary) — сохранение плана в Memory; субагенты с собственными контекстными окнами — https://www.anthropic.com/engineering/multi-agent-research-system ; LangChain (secondary) — извлечение сохранённого контекста из памяти вместо потери работы при достижении лимита — https://www.langchain.com/blog/how-and-when-to-build-multi-agent-systems

### 2.2. Тёплая (персистентная) сессия субагента с накоплением контекста
**Определение.** Субагент поднимается один раз и держится «тёплым» весь воркстрим, накапливая собственный растущий контекст между обращениями ведущего.
**Статус.** `ограниченная применимость`.
**Условие применимости.** Оправдано, когда субагент — единственный писатель связного куска состояния, дорогого для пересборки, и промежуточные состояния ведущему не нужны (пример: итеративная правка одного файла, где ведущему важен только финальный diff).
**Механизм ограничения.** Растущий контекст субагента ведёт к деградации (длина контекста сама по себе снижает качество даже при идеальном извлечении). При семантически независимых вызовах субагент тащит устаревшие допущения. Тёплая сессия реинтродуцирует второго писателя состояния — конфликт с принципом 1.4.
**Источник.** Cognition, single-writer (primary) — https://cognition.ai/blog/dont-build-multi-agents ; деградация от длины контекста — Du et al., *Context length alone hurts LLM performance despite perfect retrieval*, arXiv:2510.05381 (primary) — https://arxiv.org/abs/2510.05381

### 2.3. Расцепление слоёв: тёплый процесс/сэндбокс, холодный контекст `[вывод]`
**Определение.** Среда исполнения субагента (процесс / Docker-сэндбокс / терминал) и его когнитивный контекст (промпт + история рассуждений) — разные слои. Процесс можно переиспользовать из пула; контекст давать свежий под каждую задачу.
**Статус.** `[вывод]` из 1.2 и 2.1 в сочетании с фактом изолированного исполнения субагентов.
**Механизм.** Холодный старт контейнера и пересборка контекста — две разные статьи стоимости; они устраняются независимо. Переиспользование процесса снимает первую, свежий контекст снимает риск дрейфа (2.2).
**Источник (компоненты факта).** Hermes Agent (primary) — субагенты исполняются в изолированных контейнерах, каждый с собственным контекстом и терминалом — https://hermes-agent.org/ ; Anthropic (primary) — собственные контекстные окна субагентов — https://www.anthropic.com/engineering/multi-agent-research-system . *Само расцепление слоёв — производный вывод, отдельного источника на формулировку нет.*

## 3. Протокол на границе агентов

### 3.1. Структурированный контракт делегирования (не свободная проза)
**Определение.** Задание субагенту задаётся фиксированным набором полей: цель, формат вывода, ориентир по инструментам/источникам, границы задачи.
**Статус.** `доминирующий 2026`.
**Механизм.** Расплывчатые инструкции приводят к дублированию работы и неверной интерпретации. Зафиксированный пример: при вольных заданиях один субагент исследовал чип-кризис 2021 года, двое других дублировали запросы по цепочкам поставок 2025 года; ранние версии системы спавнили 50 субагентов на простой запрос. Требование к каждому субагенту — цель, формат вывода, ориентир по инструментам и чёткие границы задачи.
**Источник.** Anthropic (primary) — https://www.anthropic.com/engineering/multi-agent-research-system

### 3.2. Асимметрия канала и компрессия на обратном пути
**Определение.** Канал «вниз» (бриф от ведущего) может быть богатым; канал «вверх» (результат субагента) — максимально сжатый и структурированный.
**Статус.** `доминирующий 2026`.
**Механизм.** Результат субагента повторно занимает дорогой контекст ведущего, поэтому компрессия на обратном пути критична. Объём токенов объясняет ~80% дисперсии производительности — экономия на возврате прямо влияет на результат.
**Источник.** Anthropic (primary) — суть поиска есть компрессия; токены объясняют 80% дисперсии — https://www.anthropic.com/engineering/multi-agent-research-system

### 3.3. Текст — транспорт, схема — контракт `[вывод]`
**Определение.** Физически обмен идёт текстом (иного интерфейса у LLM нет), но поверх накладывается типизированная схема в обе стороны: бриф со схемой полей (3.1) и структурированный возврат (например, поля summary / handles / status / confidence).
**Статус.** `[вывод]` из 3.1–3.2.
**Механизм.** Типизированный контракт на границе агентов снижает потребность ведущего повторно интерпретировать вольный текст — что иначе жжёт его контекст и вносит ошибку. Это та же логика, что и типизация на любой API-границе.
**Источник.** Anthropic (primary) — обязательные поля брифа — https://www.anthropic.com/engineering/multi-agent-research-system . *Конкретная форма типизированного возврата — производная конкретизация, отдельного источника на именно этот набор полей нет.*

## 4. Чат как интерфейс между агентами и человеком

### 4.1. Чат как транспорт координации (data plane)
**Определение.** Агенты координируются *через* общий чат: чат является шиной сообщений, агенты читают реплики друг друга как свой вход.
**Статус.** `отвергнут 2026` (частный случай 1.3).
**Механизм.** Перечитывание полного транскрипта на каждом шаге, раздувание контекста, рассогласование между участниками.
**Источник.** Cognition, *Don't Build Multi-Agents* (primary) — https://cognition.ai/blog/dont-build-multi-agents

### 4.2. Human-in-the-loop / approval gates
**Определение.** Человек — привилегированный участник, который наблюдает обмен и может прерывать или перенаправлять; исполнение проходит через точки подтверждения (propose → approve → execute).
**Статус.** распространённый паттерн 2026.
**Механизм.** Снижает цену ошибки автономного цикла для агента с доступом к shell, браузеру и почте. Зафиксировано, что такой агент имеет shell-доступ, контроль браузера и право слать письма от имени пользователя в цикле — что и мотивирует gate перед исполнением.
**Источник.** OpenAgentsControl (primary) — approval gates, propose→approve→execute — https://github.com/darrenhinde/OpenAgentsControl ; профиль рисков агента с shell/браузером/почтой (secondary) — https://milvus.io/blog/openclaw-formerly-clawdbot-moltbot-explained-a-complete-guide-to-the-autonomous-ai-agent.md

### 4.3. Разделение data plane и control plane `[вывод]`
**Определение.** Координация агентов идёт по типизированному контракту (data plane). Человекочитаемый чат — это рендер этого обмена плюс side-channel для вмешательства человека (control plane). Корректность координации не зависит от чата.
**Статус.** `[вывод]` из 4.1 (чат-как-транспорт отвергнут) и 4.2 (human-in-the-loop полезен).
**Механизм.** Если один и тот же чат служит и транспортом, и UI, то корректность координации оказывается сцеплена с интерфейсом, что воспроизводит сбои GroupChat (1.3).
**Источник.** Производный вывод из Cognition (4.1) и OpenAgentsControl (4.2).

### 4.4. Человек инжектит через единственного писателя `[вывод]`
**Определение.** Для сохранения single-writer (1.4) человек направляет ведущего агента; если реплика человека адресована напрямую субагенту, она обязана попасть в запись, видимую ведущим, чтобы картина мира оставалась единой.
**Статус.** `[вывод]` из 1.4.
**Механизм.** Если и ведущий, и человек независимо пишут инструкции субагенту, возникает два писателя одного состояния — конфликт по 1.4.
**Источник.** Производный вывод из Cognition, single-writer — https://cognition.ai/blog/dont-build-multi-agents

## 6. Messaging-gateway: фактические возможности продуктов

### 6.1. OpenClaw (ранее Clawdbot / Moltbot)
**Факты.** Локальный персистентный демон, подключённый к 12+ мессенджерам (WhatsApp, Telegram, Slack, Signal и др.); действует через shell, браузер, почту, календарь, файлы; конфигурация — файлами (SOUL.md), модель-агностик. Зафиксировано: молодой проект; в auth-модели была серьёзная уязвимость; агент имеет shell-доступ, контроль браузера и право отправлять письма в цикле.
**Источник.** Milvus blog (secondary) — https://milvus.io/blog/openclaw-formerly-clawdbot-moltbot-explained-a-complete-guide-to-the-autonomous-ai-agent.md ; OpenClaw docs (primary) — https://docs.openclaw.ai/concepts/agent

### 6.2. Hermes Agent (Nous Research, февраль 2026, MIT)
**Факты.** Единый gateway к CLI, Telegram, Discord, Slack, WhatsApp, Signal, Matrix, Mattermost, Email и другим (16+ платформ); общая память между каналами; встроенный cron с доставкой в любой канал; субагенты в изолированных Docker-контейнерах с собственным контекстом и терминалом; пятистадийная «обучающая» петля, записывающая переиспользуемые скиллы после выполнения задачи.
**Источник.** Hermes Agent (primary) — https://hermes-agent.org/ ; Petronella review (secondary) — https://petronellatech.com/blog/hermes-agent-ai-guide/
