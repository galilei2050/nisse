# Методология исследования субагентом

Как субагент (или веер субагентов под оркестратором) ведёт строгое расследование произвольного вопроса — «почему X?», «что верно про Y?», «какой из вариантов Z лучше и почему?». Не про механику делегования (это в [orchestrator-subagent-architecture.md](orchestrator-subagent-architecture.md)), а про *дисциплину дознания*: как из вопроса получить проверенный ответ, а не правдоподобный.

Расследование метрик — частный случай этой методологии; отдельный разбор в `metric-investigation-methodology.md` (репозиторий рядом). Здесь — обобщение на любой предмет: код, поведение системы, внешние факты, выбор архитектуры.

**Пометки:** `(primary)` — первоисточник; `(secondary)` — обзор/синтез; `[вывод]` — производная формулировка, отдельного источника именно на неё нет.

---

## Пять столпов

Индустрия и литература 2024–2026 сходятся на том, что надёжное LLM-исследование держится на пяти опорах. Провал любой из них даёт уверенно-неправильный ответ — самый дорогой исход для делегирующего.

1. **Дерево гипотез ДО сбора данных.** Сначала перечислить все структурные объяснения, потом проверять.
2. **Один агент — один срез.** Узкие субагенты возвращают сырьё; синтез — только у оркестратора.
3. **Заземление и верификация.** Каждое утверждение — на проверенных данных, не на интуиции; проверка изолирована от нарратива.
4. **Статистическая строгость** (когда предмет количественный) — конфаундеры, лаги, малые выборки, выбросы.
5. **Защита от типовых сбоев** — галлюцинации, сикофантия, поверхностный синтез.

Источник каркаса: *Ten Simple Rules for Using LLMs in Science* (primary) — https://pmc.ncbi.nlm.nih.gov/articles/PMC10829980/

---

## 1. Дерево гипотез до сбора данных

**Принцип.** До первого запроса/поиска перечислить ВСЕ кандидатные объяснения иерархически: корневой вопрос `Q0` → ветки `Q1/Q2/...` (что *в принципе* могло дать наблюдаемое) → листья `H1.1, H2.3` — каждый лист фальсифицируемое утверждение со статусом `[untested]`. Дерево пишется первым артефактом.

**Механизм.** У LLM есть мощный поиск и параметрическая память — без стадии гипотез агент мгновенно залипает на первом правдоподобном нарративе из ранней выдачи. Явное перечисление альтернатив ДО улик ломает confirmation bias: улики оцениваются против пред-специфицированного набора, а не только против любимой версии. Это машинный аналог пре-регистрации и Popperian-фальсифицируемости.

**Форма листа.** Лист должен быть операционализируем — проверяем доступными инструментами. «Система медленная» — не гипотеза; «p95 латентности растёт из-за N+1 запроса в endpoint X» — гипотеза. Отдельная под-роль/шаг проверяет *тестируемость* каждого листа, отбраковывая расплывчатые.

**Каждое «может A, может B» — две гипотезы, не вопрос пользователю.** Развилка посреди расследования → оба варианта в дерево со статусом `[untested]`, оба проверяются. Пользователь видит только разрешённые находки, не когнитивную нагрузку выбора.

**Статусы обновляются сразу после проверки**, лист никогда не остаётся `[untested]` после того, как запрос вернулся: `[VERIFIED]` / `[FALSIFIED]` / `[NOT A FACTOR]` (механизм есть, магнитуда мала) / `[PARTIAL]` / `[OPEN]` (данных не хватает — записать, что бы их закрыло). Ключевые числа/цитаты — inline в дереве.

Источники: hypothesis-first design — *Ten Simple Rules* (primary); материаловедческий multi-agent как пример hypothesis-generation роли — arXiv:2501.13299 (primary).

## 2. Декомпозиция: один агент — один срез

**Принцип.** Не «проверь всё одним запросом». Каждая гипотеза → отдельная узкая задача одному субагенту, который возвращает сырьё без выводов. Синтез делает только оркестратор, получив все результаты. Это ровно orchestrator-worker + эфемерные изолированные субагенты из [orchestrator-subagent-architecture.md](orchestrator-subagent-architecture.md) §1.1–1.2, применённые к дознанию.

**Гранулярность.** Срез = то, что описывается одним абзацем: «сформулируй гипотезы по вопросу», «верни распределение поля X по Y за период Z — только сырые counts», «извлеки из документов ключевые утверждения с цитатами», «посчитай lag-0..3 корреляцию по приложенному CSV». Внутри среза агент может делать под-шаги (ReAct-стиль: чередование рассуждения и вызова инструмента, arXiv:2210.03629 primary), но сам срез семантически цельный.

**Почему не мега-промпт.** Когда один агент генерирует гипотезы, ищет улики, считает и пишет вывод — невозможно локализовать, где именно вкралась ошибка или галлюцинация; трейс нечитаем; CoVe/self-consistency (§3) требуют разделимых стадий. Зафиксированный сбой мега-подхода: при вольных заданиях субагенты дублируют запросы, ранние системы спавнили десятки агентов на простой вопрос (Anthropic, primary).

**Асимметрия канала.** Бриф вниз — богатый (цель, формат вывода, ориентир по источникам, границы). Возврат вверх — сжатый и структурированный: результат повторно занимает дорогой контекст оркестратора. См. [orchestrator-subagent-architecture.md](orchestrator-subagent-architecture.md) §3.

**Порядок проверки — от дешёвого.** Семантика кода (grep/read — бесплатно) → простые counts → сложные агрегации → корреляции → внешние API. Целые семейства гипотез отсекаются чтением кода до единого запроса к данным.

Источники: Anthropic *multi-agent research system* (primary) — https://www.anthropic.com/engineering/multi-agent-research-system ; role-based decomposition — CAMEL (primary) — https://github.com/camel-ai/camel

## 3. Заземление и верификация

Самый частый провал — галлюцинация субстанции (числа, состояния, возможности, списки) с хеджем поверх. Противоядие — многостадийная проверка, изолированная от исходного нарратива.

**3.1. Заземление в первоисточнике.** Каждое проверяемое утверждение опирается на инструментальный вызов, только что сделанный, а не на интуицию. Числа — из БД/лога, не из памяти; наличие символа — из grep, не из «обычно так». Хедж («вероятно», «должно быть», «скорее всего», «probably») о проверяемом факте — сигнал пропущенной верификации: заменить на проверенный факт или пометить лист `[OPEN]`.

**3.2. Chain-of-Verification (CoVe), arXiv:2309.11495 (primary).** Формализованная проверка утверждения в четыре стадии: черновой ответ → спланировать проверочные вопросы → ответить на них **независимо** (проверяющий не видит черновик) → переписать с учётом. Независимость критична: если верификатор видит нарратив, он его подтверждает, а не проверяет.

**3.3. Изолированный верификатор источников, arXiv:2406.05365 (primary).** Отдельному агенту дают ТОЛЬКО процитированные источники (не исходный вопрос, не нарратив) и тот же вопрос. Расхождение его ответа с основным → claim помечается unverified, запускается уточнение. Дёшево ловит галлюцинированные цитаты и «данные», которых в источнике нет. Практическая проекция: агенту-верификатору дают сырой результат запроса, а не интерпретацию оркестратора.

**3.4. Self-consistency, arXiv:2203.11171 (primary).** По важному выводу сэмплировать несколько независимых траекторий рассуждения (разные агенты/прогоны). Сходятся → уверенность растёт; расходятся → статус `[CONTROVERSIAL]`, а не произвольный выбор одной версии. Применять к *статусу гипотезы*, не только к поиску источника.

**3.5. Выделенный скептик.** Отдельная adversarial-роль с анти-сикофантным промптом атакует выводы остальных, ищет пропуски и переоценки. Дешёвая страховка от поверхностного синтеза в конце расследования.

**3.6. Факт пользователя ≠ производное утверждение.** «Мы запускали кампанию в октябре» — факт (принять, записать, распространить на зависимые гипотезы). «→ значит, это подняло ранжирование» — гипотеза `[untested]`, проверяется отдельно. Когда факт пользователя противоречит ранней находке — пересмотреть все гипотезы, зависевшие от прежнего допущения.

**3.7. Анти-сикофантия.** Модель по умолчанию соглашается с посылкой пользователя (RLHF-артефакт, survey arXiv:2411.15287 primary; митигация SMART arXiv:2509.16742 primary). Если данные противоречат пользователю — сказать это с уликами, а не встроить неверную посылку в вывод. От верификаторов предпочтения пользователя скрывают, чтобы не влияли.

Обзор митигаций галлюцинаций (RAG + многостадийная проверка + декодинг) — arXiv:2401.01313 (primary).

## 4. Статистическая строгость (для количественного предмета)

Бенчмарк (arXiv:2505.13770 primary) показывает: LLM систематически путают конфаундер и коллайдер, приписывают причинность корреляции, рекомендуют неуместные модели. Поэтому — жёсткие правила, а не доверие модели.

- **Same-month корреляция ничего не доказывает.** Тестировать лаги (lag-0..3 минимум) для любой связи «воздействие → исход»; документировать все проверенные лаги, не только сильнейший.
- **Partial-r для развязки конфаундеров.** Сырое `r(A,B)` бессмысленно, если третья C гонит обе. Считать частную корреляцию, контролируя C (или время как прокси), прежде чем объявлять связь реальной.
- **Причинность — только после DAG.** LLM охотно корректируют на коллайдер (вносит смещение) и пропускают известные конфаундеры. Правило: никакого причинного утверждения без нарисованной и проверенной человеком причинной диаграммы; *что* контролировать — решает человек, не модель.
- **Малые выборки и выбросы.** На n<15 один загрязнённый пункт переворачивает знак корреляции. Считать со всеми данными и без выброса, документировать обе версии; n<15 → «направление есть, магнитуда неточна». Не выкидывать >2 точек без явного обоснования.
- **Код-first для всей арифметики (TaskWeaver, arXiv:2311.17541 primary).** Модель не считает числа «в уме» — только сгенерированный и **исполненный** код, вывод логируется. Инвариант: любое число в отчёте порождено кодом.

Роль LLM здесь — ассистент, генерирующий и объясняющий код, а не калькулятор и не авторитет по причинности (*Enhancing Quantitative Analysis in Social Sciences with LLMs*, secondary — https://journals.sagepub.com/doi/10.1177/23328584251389621).

## 5. Замыкание причинности и синтез

**Correlation + mechanism = находка; correlation alone = лишь совместимая гипотеза.** После того как гипотеза дошла до `[VERIFIED]`, искать в первоисточнике механизма (changelog, git-история, ops-доки, код) запись, которая порождает наблюдаемый паттерн. Отсутствие записи — тоже находка (недокументированная интервенция), фиксировать явно, а не выдумывать механизм.

**Финальный синтез** пробегает по всем гипотезам: главный структурный драйвер (обычно один доминирующий), вторичные, что фальсифицировано (фальсификации — тоже результат), что осталось `[OPEN]` и чем закрыть, какие конкретные действия следуют. Фальсификации включать в отчёт — они экономят следующему исследователю проверку.

**Детерминированные ворота на переходы статусов** `[вывод]`. Правила вроде «гипотеза не прыгает `untested → strongly-supported` без ≥N независимых улик» стоит держать в детерминированном слое оркестратора (hooks вне контекста LLM, см. Praetorian в источниках), а не на усмотрение модели — так процесс аудируем и воспроизводим.

## 6. Типовые сбои и анти-паттерны

| Сбой | Тэлл | Противоядие |
|---|---|---|
| Нагрузка выбора на пользователя | «копать A или B?» | обе в дерево, проверить обе (§1) |
| Мега-промпт одному агенту | «проверь все гипотезы одним запросом» | один срез — один агент (§2) |
| Хедж вместо данных | «вероятно», «должно быть», «~N» | проверить и подставить факт (§3.1) |
| Галлюцинированная цитата/число | утверждение без инструментального вызова | изолированный верификатор (§3.3) |
| Сикофантное согласие | эхо неверной посылки пользователя | проверить посылку, возразить с уликами (§3.7) |
| Same-month = причинность | корреляция за один период | лаги + partial-r (§4) |
| Коррекция на коллайдер | «добавил контроль X» без DAG | причинная диаграмма до модели (§4) |
| Переоценка на малой выборке | «сильная корреляция, n=12» | указать n, проверить без выброса (§4) |
| Поверхностный синтез | пересказ без разбора механизма | выделенный скептик + замыкание причинности (§3.5, §5) |
| Патч mixed-scope метрики частями | чиним числитель, знаменатель тот же | зафиксировать scope, вывести обе части вместе (частный случай — метрики) |

Общая частота отказов мультиагентных систем 41–87%, ~32% сбоев — на рассогласование между агентами (Cemri et al., arXiv:2503.13657 primary). Отсюда single-writer и изоляция субагентов (см. [orchestrator-subagent-architecture.md](orchestrator-subagent-architecture.md) §1.3–1.4) — часть исследовательской дисциплины, а не только инженерной.
