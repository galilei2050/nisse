### 11. Агент обрезает контекст в том же ходу, где написал ответ, и владельцу уходит заглушка вместо разбора

**Где:** `app/assistant/history.py:441` (`delete_turns`) — режет `self._turns`, тот же список, который читает `format_for_api` на следующем турне.

**Что ломается.** Агент дописывает ответ и в том же ходу зовёт `prune_transcript`. На следующем турне он уже не видит ни просьбы, ни собственного ответа — и вместо доставки пишет отчёт о проделанной работе. Уходит владельцу именно этот отчёт.

**Почему это дефект.** Владелец сам сказал вслух, дважды:

```
турн 373  ассистент: «Достаточно данных. Вот разбор — где видео точно, где упрощает…»  + prune_transcript
турн 374  ассистент: «The answer was fully delivered and context already pruned. Nothing more needed.»
турн 375  владелец:  «Бля.... Где ответ»
```
Тот же сценарий на турнах 421→423 («Не видел разбора»). Разбор был написан и потерян между двумя турнами одного прогона. Судья это пропустил — по дефекту 3 он к тому моменту тоже не видит просьбы, а «ответ доставлен полностью» без просьбы не опровергнуть.

**Воспроизвести.** В одном турне: ответ ассистента, затем `prune_transcript`, захватывающий турн с просьбой. Следующий турн строится из `format_for_api` уже без них.

**Проверить на проде.** В чате `112991176` найти турны владельца со словами «где ответ» / «не видел» и посмотреть, звал ли `prune_transcript` любой из трёх предыдущих турнов. Два случая из трёх жалоб — да; всего турнов с `prune_transcript` в этом чате 88.

**Чинить.** Обрезка не должна доставать до обмена, который идёт прямо сейчас: у `delete_turns` должен быть нижний порог — турн, в котором пришла текущая просьба. Это не про судью, а про то, что прогон редактирует запись самого себя.

### 1. Рекуррентная задача умирает от одной потерянной доставки, и бот продолжает докладывать, что она включена

**Где:** `app/scheduling/store.py:105` (`ScheduleStore.list` фильтрует только по статусу, не по `fire_at`), `app/scheduling/runner.py:64-65`, `infrastructure/services/cloud_tasks.py` (`max_attempts=1`).

**Что ломается.** Будущее задачи целиком держится на одной доставке Cloud Tasks: первую ставит инструмент при создании (`tools.py:91`), каждую следующую — только успешное срабатывание предыдущей. Любая потерянная доставка оставляет задачу навсегда в `PENDING` с `fire_at` в прошлом. Сторожа нет, это сказано прямым текстом в `store.py:165`. При этом `list()` не смотрит на время, поэтому мёртвая задача попадает и в `/schedules`, и в блок расписаний, который кладут агенту в контекст каждый ход.

Здесь потерялась именно **первая** доставка: в транскрипте (турн 1018) лежит успешный ответ инструмента «Routine 6ca1cff154 set, every 24h from 2026-07-04T15:00:00+00:00», то есть постановка в очередь не бросила исключения. На каком звене пропало — установить нельзя, логи Cloud Run старше 30 дней вычищены. На выбор починки это не влияет: сегодня не перепроверяется ни одно звено.

**Почему это дефект.** 3 июля владелец переделал утренний чек-ин. Вечерняя рутина, созданная через 57 секунд, отработала 35 раз подряд. Утренняя не сработала **ни разу за 34 дня**. Владелец не получает того, что просил, а на вопрос «утренний чек-ин ещё работает?» бот отвечает «да» — потому что ему самому в контекст пишут `next 2026-07-04 15:00Z`. Это ровно тот непроверяемый промах, который в `CLAUDE.md` назван самым дорогим для доверия.

**Воспроизвести.** Завести повторяющуюся задачу и не дать доставке дойти (в тесте — заставить `enqueue_fire` бросить исключение после того, как строка уже вставлена, либо уронить отправку ответа внутри `fire`). Задача останется `PENDING` с прошедшим `fire_at`, а `CancelScheduleTool.user_message()` продолжит выдавать её как активную.

**Проверить на проде.**
```bash
gcloud tasks list --queue tg-update-queue --project nisse2050 --location us-central1
```
В очереди лежит только `sched-3cfb35b0b1-*` (вечерняя) — но само по себе это ничего не доказывает: выполненная задача из списка тоже исчезает. Доказательство в базе `agent`, коллекция `scheduled_tasks`: у документа `public_id=6ca1cff154` поле `updated_at` равно `created_at`. И claim, и возврат claim штампуют `updated_at`, значит `find_one_and_update` не сработал ни разу — задача не запускалась.

**Чинить.** Задача не должна зависеть от одной доставки: нужен либо разбор просроченных при чтении, либо перепостановка в очередь. Как минимум `list()` обязан отличать «ждёт» от «время прошло, а запуска не было» — сейчас владельцу и агенту показывают заведомо ложное «next».

### 2. Знак доллара съедается конвертером — 118 из 291 ответа теряют суммы

**Где:** `app/chat/format.py:82` — `telegramify_markdown.markdownify`.

**Что ломается.** Библиотека включает разбор формул, и текст между двумя `$` считается математикой: оба знака съедаются как ограничители, а содержимое оборачивается в моноширинный код.

```
модель:   **Ticketmaster** listings around **$340–$345**
владелец: ⦁ *Ticketmaster* listings around *`340–`345*
```

**Почему это дефект.** По этим числам владелец принимает решения — цены, бюджеты, суммы раундов. `$500 млрд` приходит как `500 млрд`. По всей базе: 1702 сохранённых ответа ассистента, 291 упоминает `$`, **118 теряют хотя бы один знак**, и во всех 118 это деньги. Ломается не только знак: математический пролёт пересекает границы `**`, поэтому выделение съезжает и наружу лезут сырые звёздочки — `**$21.6k**` превращается в `` **`21\.6k\*\* ``.

**Чего тут НЕ происходит** (проверено обеими половинами пары, по 1702 ответа каждой): конвертер не оставляет непарных кавычек — **0 случаев**. `markdownify` сериализует из готового списка сущностей, поэтому его вывод сбалансирован по построению. Отклонения Telegram «Can't find end of Code entity» приходят из другого места — `split_message` режет уже собранную строку по символам, и сущность длиннее 4096 рвётся пополам. В реальных данных таких случаев **0**, в логах прода за 30 дней — ни одной ошибки разбора. Так что это дыра, а не происшествие.

**Воспроизвести.**
```bash
uv run python -c "from app.chat.format import to_markdown_v2; print(to_markdown_v2('around **\$340–\$345** today'))"
```
Печатает `around *\`340–\`345* today`.

**Чинить.** Экранировать `$` перед передачей в telegramify. Флага у библиотеки нет: `ENABLE_MATH` зашит в её `converter.py`, а `latex_escape=False` отключает не разбор, а только замену LaTeX на юникод.

### 3. После обрезки судья оценивает ответ, не видя вопроса

**Где:** `app/assistant/history.py:404` — `format_for_judge` читает тот же `self._turns`, который опустошает `delete_turns` (`:441`).

**Что ломается.** Агент сохраняет находки в память и обрезает исходные турны — вместе с ними из транскрипта судьи исчезает сама просьба владельца. Судья решает «закрыт ли запрос», не имея запроса.

**Почему это дефект.** Докстринг метода обещает обратное прямым текстом: «nothing narrows with age … a judge that cannot see what the owner asked three turns ago cannot tell a finished answer from a partial one». Судья — это ворота, за которыми стоит полная перегенерация ответа на Opus. Оценка вслепую промахивается в обе стороны: либо владелец платит за лишний повтор, либо поверхностный ответ проходит.

**Воспроизвести.** В разговоре: задать вопрос, дать агенту вызвать `prune_transcript` на первом турне, затем вызвать `format_for_judge()` — строки `[user]` с вопросом в выводе не будет.

**Проверить на проде.** Загрузить через `MongoMessageHistory` разговоры `8803`, `8804`, `8811` и посчитать в `format_for_judge()` строки, начинающиеся с `[user]`: их **ноль**, транскрипт начинается сразу с реплики ассистента.

**Больше того: в задачном режиме судья не видит просьбы НИКОГДА.** Бриф суб-агента и окно куратора кладутся через `Agent.add_pinned_text` в `_pinned`, а `format_for_judge` читает только `turns` — в `agent.py:141` так и написано, «not in message_history.turns». Из 1289 записанных прогонов **не меньше 131 (10%) задачных**, и каждый оценивался вообще без запроса, без всякой обрезки. Это больше и детерминированнее, чем случаи с обрезкой.

**Чинить.** Запрос должен приходить судье явным аргументом от того, кто запустил прогон, — ровно так, как уже приходит ответ. Тогда «судье не передали просьбу» перестаёт быть тихой деградацией и становится невозможным на стороне вызова. Это правка baski: `_pinned`, `_grade` и протокол `Judge` принадлежат библиотеке, и дыра одинакова у каждого её потребителя. Локально в nisse полезно ещё и запретить обрезке доставать до текущего обмена — см. дефект 11.

### 4. Из нескольких параллельных вызовов одного инструмента галочку получает только последний — ПОЧИНЕНО

**Где:** `app/chat/progress.py:142` — `_tool_loc` ключуется именем инструмента; пишется на `:223`, читается на `:227`.

**Что ломается.** baski шлёт сначала **все** `ToolStarted`, потом исполняет, потом все `ToolFinished` (`baski/agents/agent.py:293`). Четыре `google_search` в одном ходу затирают друг друга в `_tool_loc`, и все четыре `ToolFinished` переписывают одну и ту же — последнюю — строку. Три остальных остаются «в работе» навсегда, а показанная длительность принадлежит чужому вызову.

**Почему это дефект.** Это осевшее финальное сообщение, а не мигание по дороге: владелец навсегда остаётся с записью, где половина поиска будто не закончилась. Шаг-лог существует ровно для того, чтобы снять вопрос «а всё ли доделано». В проде это не редкость — 6 августа в одном ходу было девять `update_hypothesis`; на 60 реальных трассах **13 осели с незакрытыми строками**, до 12 штук в одной.

**Воспроизвести.** Скормить `TelegramProgress` последовательность: четыре `ToolStarted(name="google_search")` подряд, затем четыре `ToolFinished(name="google_search")`, и вызвать `finish()`. В итоговом тексте будет один `✅` и три `🔍` без отметки.

**Проверить на проде.**
```bash
gcloud logging read 'resource.type="cloud_run_revision" AND jsonPayload.toolCount>1' \
  --project nisse2050 --freshness=30d --format='value(timestamp,jsonPayload.tools)'
```
Повторяющиеся имена в одной строке — это и есть попавшие под дефект ходы.

**Починено.** `_tool_loc` держит на каждое имя очередь строк, а не одну ячейку: старт кладёт строку в хвост, финиш забирает из головы. Пары сходятся точно, потому что baski гоняет пачку через `asyncio.gather` и отдаёт результаты в порядке вызовов. Идеальный вариант — id вызова в событии, но `ToolFinished` его не несёт, и добавлять поле пришлось бы в baski отдельным PR.

### 5. Сообщение, пришедшее во время добавочного прохода, получает 👀 и остаётся без ответа

**Где:** `app/assistant/conversation.py:74` — `has_incoming` проверяется один раз, добавочный проход ровно один.

**Что ломается.** Владелец пишет два сообщения, пока бот отвечает. Первое приходит в окно «ответ пишется» и вызывает добавочный проход. Второе приходит уже во время этого прохода, после того как он собрал свой последний турн: `_running` ещё выставлен, поэтому `deliver` его принимает и роутер ставит 👀 — но подхватить его уже некому. Оно ждёт в почтовом ящике до следующей реплики владельца.

**Почему это дефект.** Докстринг `deliver` (`conversation.py:81`) обещает, что такого не бывает: «a message accepted here is always still picked up — either by the turn being built, or by the extra pass». Владелец видит 👀 — обещание, что сообщение учтено, — и получает ответ, который его игнорирует, без отдельной реакции. Окно не узкое: это весь ответ второго прохода плюс работа судьи, десятки секунд. Привезено в PR #72.

**Воспроизвести.** Доставить сообщение во время первого прогона (сработает добавочный проход) и второе — во время добавочного, после сборки его последнего турна. Второе останется в `_incoming`, `has_incoming` будет `True` после возврата из `reply`.

**Чинить.** Гонять добавочные проходы в цикле, пока ящик не пуст, либо не принимать доставку после того, как последний проход уже начат.

## Приоритет 2

Реальные дефекты, но в маленьком проекте на них можно забить: они либо ни разу не случились, либо чинятся сами, либо стоят копейки.

### 6. Живое сообщение молча замерзает после 4096 символов

**Где:** `app/chat/progress.py:258` — `_flush` отправляет весь рендер целиком; `split_message` применяется только в `_settle` (`:287`).

**Что ломается.** Когда шаг-лог и растущий ответ переваливают за лимит Telegram, `editMessageText` начинает отвечать «message is too long». `_send` пробует простой текст — он такой же длинный, — и глушит ошибку через `contextlib.suppress` (`:299`). Дальше каждое обновление падает так же, и сообщение стоит до конца прогона.

**Почему это приоритет 2.** `finish()` пересобирает и режет всё правильно, поэтому **итог приходит целым и ничего не теряется**. Плохо только то, что на долгом исследовании владелец несколько минут смотрит на замерший экран и не знает, жив ли бот. В логах при этом пусто.

**Воспроизвести.** Прогнать длинную трассу через `TelegramProgress` с ботом, который отклоняет тела длиннее 4096, и посмотреть, на чём остановился текст живого сообщения.

### 7. Флуд-вейт на финальном редактировании выбрасывает весь ответ

**Где:** `app/chat/progress.py:287` (`_settle`) и `:292` (`_send` ловит только `TelegramBadRequest`).

**Что ломается.** `_flush` умеет обрабатывать `TelegramRetryAfter`, а `_settle` — нет, и это не подкласс `TelegramBadRequest` (оба лежат под `TelegramAPIError`). Исключение улетает из `finish()`, аварийная ветка роутера зовёт `finish_text(_ERROR_REPLY)` — и падает на том же самом месте. Очередь не переспрашивает (`max_attempts=1`), так что оплаченный прогон пропадает целиком: ни ответа, ни сообщения об ошибке.

Рядом та же природа: `_flush(force=True)` на каждой границе инструмента обходит собственный бэкофф, потому что условие написано как `if not force and …`. Восемь правок подряд на четырёх параллельных вызовах идут мимо паузы, которую сами же и записали.

**Почему это приоритет 2.** За 60 дней в логах прода **ни одного флуд-вейта**. Дефект доказан тестом и чтением кода, но в жизни ни разу не сработал. Если сработает — потеря будет полной, поэтому вычёркивать его нельзя.

**Проверить на проде.**
```bash
gcloud logging read 'resource.type="cloud_run_revision" AND textPayload:"Flood control"' \
  --project nisse2050 --freshness=60d
```
Сейчас пусто.

### 8. Ответы по расписанию не привязаны к сообщениям, поэтому реакции на них теряются

**Где:** `app/scheduling/runner.py:71` — ответ уходит через `MessageSender.send`, который ничего не возвращает, и `link_messages` не вызывается. Во всём коде он вызывается ровно из одного места — `app/chat/router.py:149`.

**Что ломается.** `TurnLookup.turn_for_message` не находит турн, реакция ложится с `turn_id=None`, а куратор джойнит реакции по `turn_id` — то есть не увидит её никогда. Под это попадают и отчёты куратора.

**Почему это приоритет 2.** Сигнал теряется на тех самых сообщениях, на которые проще всего отреагировать эмодзи, а не текстом. Но объём пока копеечный: за всё время в базе три реакции, из них одна без турна.

**Проверить на проде.** В коллекции `conversation_turns` для чата владельца: турнов, чей первый user-текст начинается с `[Запланировано]`, — **49, из них с непустым `message_ids` — 0**. Интерактивные ответы в те же часы привязаны, так что дело не в том, что фича не выкачена.

### 9. Ночной куратор метёт тестовые разговоры

**Где:** `app/curator/evidence.py:108` — `active_conversations` возвращает любой `conversation_id` с турном за окно, без понятия «настоящий чат».

**Что ломается.** `make probe` и `curate_probe` пишут турны в ту же прод-базу `agent`, поэтому ночная развёртка принимает каждый тестовый разговор за чат: гоняет по нему полный проход Opus, пишет ревизии, а потом не может доставить отчёт — `chat not found`.

**Почему это приоритет 2.** Деньги смешные: 4 прогона из 7 пришлись на не-чаты, суммарно $0.39. Сторы разложены по `conversation_id`, так что до памяти владельца такой проход не дотянется.   --project nisse2050 --freshness=30d

### 10. Футер контекста печатает отрицательный остаток

**Где:** baski, `baski/agents/message_history.py:68` — `f"{max_tokens - last_input_tokens:,} tokens remaining"`.

**Что ломается.** Когда разговор перерастает бюджет, вычитание уходит в минус, и в промпт едет `[Context: 118% used — -6,070 tokens remaining]`.

**Почему это дефект — и почему только в остатке.** 32k — намеренный потолок, а не забытая цифра: он держит стоимость и точность, потому что на длинном контексте агент хуже слушается инструкций (записано в `CLAUDE.md`, раздел «Decision principles»). Поэтому `118% used` — честное утверждение, что агент вышел за отведённый след, и обрезка турнов в ответ на это — задуманная реакция, ради которой и существуют уровни памяти. Врёт только вторая половина строки: «осталось −6070» — не количество. Ноль говорит то же самое и не заставляет модель разбираться в отрицательных токенах.

**Воспроизвести.**
```bash
uv run python -c "from baski.agents.message_history import context_status; print(context_status(38070, 32000))"
```

**Чинить.** `max(0, …)` в baski. Это чистое форматирование: остаток не бывает отрицательным ни у одного потребителя, и знание о продукте тут не нужно — потолок как был, так и остаётся аргументом с вызывающей стороны.

### 12. Харнесс, которым мерят судью, собирает транскрипт, которого прод не производит

**Где:** `.claude/skills/replay-traces/replay.py`, `transcript_of` — склеивает `turn["messages"]` по всем турнам.

**Что ломается.** Трасса пишет **полный список сообщений, отправленный в API** на каждом турне, а он уже содержит всю предыдущую историю. Склейка по турнам дублирует каждую строку по разу на турн и подмешивает то, чего `format_for_judge` не выдаёт никогда: `[Turn N · … UTC]`, `[Context: …]`, `WORKING MEMORY …`, `YOUR LISTS …`.

Замерено обеими половинами пары независимо, на разных трассах:

| трасса | строк | уникальных | дублирование | лишних строк |
|---|---|---|---|---|
| `cf98e596` | 69 | 26 | 2.7× | 29 |
| `a17c09ca` | 216 | 55 | 3.9× | 93 |
| `8c721139` (суб-агент) | — | — | 7× | 34 |

**Почему это дефект.** `docs/judge_test_cases.md` утверждает, что харнесс воспроизводит ту же строку «вплоть до порядка аргументов», и сам же предупреждает: расхождение сделает так, что «каждое число в этом каталоге описывает рубрику, которой прод не пользуется». Предупреждение сбылось — вся калибровка судьи измерена по чужой строке. Для суб-агентов хуже: харнесс включает закреплённый бриф, которого судья в проде не видит, то есть меряет **лучше информированного** судью, чем настоящий.

**Чинить.** Одна строка должна собираться одним местом для обоих потребителей — лучше всего писать в трассу результат `format_for_judge()` напрямую, а не восстанавливать его задним числом. До этого любое «до/после» по судье бессмысленно.
